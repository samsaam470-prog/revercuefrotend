# REVERCUE — THE SCREEN WORKFLOW
# File: workflow.txt
# Purpose: The screen-to-screen flow. What happens after each action, every transition, every state.
# Audience: The AI building the frontend. Read architecture.txt and publicsite.txt first.
# Every screen has: the entry (how the user arrives), the actions (what they can do), the exit (where each action goes), the states (empty, loading, error, success).
# The rule: no screen without a defined exit. Every button goes somewhere. Every form has a success state and an error state.

# ============================================================
# PART 1 — THE PUBLIC VISITOR FLOW
# ============================================================

## Flow P1 — Home -> Sign Up
Entry: the visitor lands on / (Home).
Actions: read the hero, scroll to the features, the pricing teaser, the FAQs, click "Start Free".
Exit: /signup. The "Start Free" CTA is gold, in the header and in the hero. The "See Pricing" ghost goes to /pricing.
States: the FAQ "Show all 49" expands inline (no navigation). The pricing chips are links to /pricing.

## Flow P2 — Pricing -> Sign Up or Waitlist
Entry: /pricing.
Actions: read the five cards, the comparison table, the billing FAQs, click a plan CTA.
Exit: Free/Starter/Growth/Scale CTAs -> /signup. The Teams CTA -> the waitlist modal (email only), then a toast "You're on the list. We'll be in touch."
States: the comparison table scrolls horizontally on mobile. The waitlist modal has email validation, a loading state, a success state, an error state.

## Flow P3 — Guides -> Guide -> Sign Up
Entry: /guides.
Actions: read the guide cards, click one.
Exit: /guides/:slug. The guide page has a sticky TOC on desktop, a "Start Free" CTA at the end. The CTA goes to /signup.
States: the guide page is static, no loading. The CTA is the only interactive element.

## Flow P4 — Contact -> Success
Entry: /contact.
Actions: fill the form (name, email, topic, message), click "Send message".
Exit: on submit, POST /api/contact. On success, the form is replaced by the success state: "Thanks. We read every message. We'll reply to [email] within 1 business day." + "Send another" ghost. On error, the form stays, the error is shown below the button.
States: the button is disabled until name, email, message are filled and the email is valid. The loading state is a spinner in the button. The success state replaces the form. The error state is a red line below the button.

## Flow P5 — Beta -> Success
Entry: /beta.
Actions: fill the form (name, email, account type, services, proposals/month, what to test), click "Apply for beta".
Exit: on submit, POST /api/beta. On success, a success state: "Thanks. We review every application. If you're a fit, you'll hear from us within 5 business days." On error, the form stays with the error.
States: the services is a checkbox group (at least one). The "what to test" is optional. The button is disabled until the required fields are filled.

## Flow P6 — Any public page -> Log In
Entry: the header "Log in" on any public page.
Exit: /login. The "returnTo" is the current path, so after login the user returns to where they were.

# ============================================================
# PART 2 — THE SIGNUP FLOW (the first real user action)
# ============================================================

## Flow S1 — Sign Up form
Entry: /signup. The minimal header (logo only, back-arrow to Home).
Actions: fill email, password, check TOS (required), optionally check newsletter, click "Create account" or "Continue with Google".
Exit: on submit, POST /api/auth/signup.
  Success: the response has a pre-auth token. The app stores it in sessionStorage. It navigates to /signup/transition.
  Error 409 (conflict): the email is already registered. Show "This email is already registered. Log in instead?" with a link to /login.
  Error 400 (invalid_payload): the email is invalid or the password is too short. Show the inline error below the field.
  Error 429 (rate_limited): "Too many attempts. Try again in a minute."
States: the "Create account" button is disabled (50% opacity) until TOS is checked. The password strength bar fills as the user types. The Google button opens the Google OAuth flow, then returns to /signup/transition on success.

## Flow S2 — Signup transition (5 seconds)
Entry: /signup/transition. The user has just signed up.
Content: full-page, bg-base, a gold spinner, the exact FormSubmit copy:
  "Check your inbox. FormSubmit will send you an activation email. That activation email lets us know that you are open to transactional emails, app notifications, and security alerts. This activation will not opt you in to the newsletter."
Actions: none. The screen auto-advances after 5 seconds (or when the Worker responds) to /signup/code.
Exit: /signup/code.
States: the spinner is the only motion. No buttons, no links. The user reads the copy.

## Flow S3 — Signup code screen
Entry: /signup/code. The pre-auth token is in sessionStorage.
Content: six code boxes, the prominent gold-bordered FormSubmit message (the exact copy above), the countdown (5:00), "Verify" (gold), "Resend code" (ghost, disabled 90s with a countdown), the persistent disclaimer below.
Actions:
  Enter the 6 digits -> "Verify" becomes enabled. On click, POST /api/auth/verify-email with the code and the pre-auth token.
    Success: the response has the full user JWT. Store it. Navigate to /onboarding/step-1.
    Error 400 (invalid_code): "Incorrect code. 2 attempts remaining." The attempts decrement.
    Error 429 (too_many_attempts): "Too many attempts. Try again in 15 minutes."
    Error 400 (code_expired): "The code expired. Click Resend."
  "Resend code" -> after 90s, POST /api/auth/resend-verification. On success, a toast "Code sent. Check your inbox." and the countdown resets. On error 429 (cooldown_active), show the retry_after in the button label.
Exit: on verify success, /onboarding/step-1.
States: the countdown ticks down. The "Resend" is disabled with the remaining seconds. The error is a red line below the boxes. The loading state is a spinner in the "Verify" button.

# ============================================================
# PART 3 — THE ONBOARDING FLOW (the 5 steps)
# ============================================================

## Flow O1 — Step 1 (Freelancer or Agency)
Entry: /onboarding/step-1. The user has a full JWT and email_verified = true.
Content: two large cards (Freelancer, Agency), "Continue" (gold, disabled until one is selected).
Actions: select a card -> "Continue" enabled. On click, PATCH /api/onboarding/step-1 with account_type.
Exit: /onboarding/step-2. The response has onboarding_step = 2.
States: the selected card has a gold border and a light gold background. The unselected card is bg-card with 1px border.

## Flow O2 — Step 2 (profile)
Entry: /onboarding/step-2.
Content:
  If Freelancer: name, business name, email (read-only), services (checkbox group), proposals per month (dropdown), website (optional), Fiverr profile (optional).
  If Agency: name, agency name, email (read-only), agency size, services, proposals per month, website (optional), brand colours (optional).
  "Continue" (gold).
Actions:
  Fill the fields -> "Continue" enabled when name is filled.
  If website is blank on Continue: an inline message "You didn't add a website. Do you have one?" with three options: add it (re-focus the field), skip (continue), "I need help" (opens the website-help inline form: website type, timeline, notes; POST /api/website-help; then continue).
  On Continue, PATCH /api/onboarding/step-2 with the profile.
Exit: /onboarding/step-4 (the legal consent step).
States: the services is a checkbox group (at least one). The volume dropdown is 1–3, 4–10, 11–20, 20+. The email field is read-only with a grey background and a helper "To change your email, contact support."

## Flow O3 — Step 4 (legal consent)
Entry: /onboarding/step-4.
Content: the TOS + Privacy checkbox (pre-checked from signup), the newsletter checkbox (pre-checked from signup), "Continue" (gold).
Actions: on Continue, PATCH /api/onboarding/step-4 with newsletter_opt_in.
Exit: /onboarding/step-5.
States: the TOS checkbox must stay checked. If the user unchecks it, "Continue" is disabled with a message "You must accept the Terms to continue."

## Flow O4 — Step 5 (plan selection)
Entry: /onboarding/step-5.
Content: five plan cards (Free, Starter, Growth, Scale, Teams). The "Recommended" badge on the plan that matches the "proposals per month" answer (1–3 -> Free, 4–10 -> Starter, 11–20 -> Growth, 20+ -> Scale). Free is selected by default. The paid plans show "Join Waitlist" (opens the waitlist modal, email only). "Continue" (gold).
Actions: select a plan -> Continue. On Continue, PATCH /api/onboarding/step-5 with plan (free) or plan_requested (the waitlist plan).
Exit: /dashboard. The onboarding_step is now 6. The tutorial starts.
States: the selected plan has a gold border. The paid plans have a "Join Waitlist" ghost button instead of a "Select" button. The waitlist modal has email validation and a success toast.

## Flow O5 — The tutorial (overlay on the dashboard)
Entry: /dashboard, after onboarding step 5. The tutorial is an overlay with a dimmed background.
Content: 10 steps (Welcome, New Proposal, New Contract, New Form, New Invoice, Recent Activity, Follow-ups Due, CRM, Settings, Done). Each step is a popover anchored to the element it describes.
Actions: "Next", "Back", "Skip", "Done". On Done or Skip, PATCH /api/onboarding/tutorial with completed or skipped.
Exit: the overlay closes. The dashboard is visible. The FormSubmit activation banner appears (if formsubmit_activated = false and banner_dismissed = false).
States: the overlay is focus-trapped. Escape does not close it (it is a tutorial). The "Skip" is a ghost text button. The "Done" is gold.

# ============================================================
# PART 4 — THE DASHBOARD FLOW
# ============================================================

## Flow D1 — Dashboard Overview (the first load after onboarding)
Entry: /dashboard.
Content: the FormSubmit banner (if not activated), the greeting, the 4 stat cards, the pending payments line, the suggested actions (Growth/Scale), the create row, the recent activity, the empty state (if no data).
Actions:
  Click a stat card -> the filtered list (/proposals?status=published, /crm, /crm?filter=follow-ups-due, /invoices?status=confirmed).
  Click the pending line -> /invoices?filter=pending.
  Click a suggestion "Do it" -> the suggestion's action (open the client record, create the contract, etc.).
  Click a suggestion "Dismiss" -> the suggestion is removed for that client/document.
  Click "Create proposal" -> the proposal requirement form (/proposals/new).
  Click "Create contract" -> /contracts/new. "Create invoice" -> /invoices/new. "Create form" -> /forms/new.
  Click an activity item -> the client record or the document.
  Click the FormSubmit banner "I clicked the activation link" -> PATCH /api/settings/formsubmit-activate; the banner disappears. Click "×" -> the banner disappears (banner_dismissed = true).
Exit: the routes above.
States: the stat cards show a skeleton while loading. The suggestions show a skeleton while loading. The activity feed shows the empty state "Nothing yet." The first-login empty state replaces sections 3–7.

## Flow D2 — Proposals list
Entry: /proposals (or from the dashboard stat card).
Content: the table (title, client, status badge, last activity, actions), the filter bar (All/Drafts/Published/Archived), the search, the "Create proposal" (gold) top-right.
Actions:
  Click a row -> the proposal builder (/proposals/:id/edit).
  Click "Create proposal" -> the requirement form (/proposals/new).
  Click the ⋮ -> Duplicate (POST /api/proposals/:id/duplicate; a toast; the list refreshes), Archive (POST /archive; a confirmation modal; the list refreshes), Delete (DELETE; a confirmation modal; the list refreshes).
  Type in search -> the list filters live (debounced).
  Click a filter -> the list filters by status.
Exit: the builder, the requirement form.
States: the table shows a skeleton while loading. The empty state "No proposals yet. Create your first proposal." + the CTA. The error state "Could not load proposals. Retry." with a retry button.

## Flow D3 — The proposal requirement form
Entry: /proposals/new. The user clicked "Create proposal".
Content: the client selector (Existing client searchable dropdown / New client name+email), the problem textarea, the sections checkboxes, the FAQs upload (if FAQs checked), the questions upload (if Embedded Questions checked), the currency, the timeline, the tone, "Continue to builder" (gold).
Actions:
  Select an existing client -> the fields pre-fill. Select "New client" with an email already in the CRM -> a suggestion "This email exists. Use [Client]?"
  Fill the required fields -> "Continue" enabled.
  On Continue, POST /api/proposals/draft. The response has the draft ID.
Exit: the template selection screen (/proposals/:id/edit?step=template), then the builder canvas.
States: the "Continue" is disabled until client + problem + at least one section. The errors are inline below each field. The loading state is a spinner in the button.

## Flow D4 — The template selection
Entry: /proposals/:id/edit?step=template.
Content: the template cards (thumbnail, name, one-line description, "Suggested" gold badge if the tags match the user's services), "Start from blank", "Upload your own template" (Growth/Scale), "Use a template from a URL" (Growth/Scale).
Actions:
  Click a template card -> the builder canvas loads with the template rendered and the placeholders filled (/proposals/:id/edit).
  Click "Start from blank" -> the canvas opens empty, with the requirement form data in the suggestions panel (/proposals/:id/edit?blank=true).
  Click "Upload your own template" -> a modal (HTML file or URL); POST /api/templates/upload; the template appears in the list.
  Click "Use a template from a URL" -> a field; POST /api/templates/upload with the URL; the template appears.
Exit: the builder canvas.
States: the template cards show a skeleton while loading. The upload modal has file validation (HTML, max size) or URL validation. The error state "Could not upload the template. Retry."

## Flow D5 — The builder canvas
Entry: /proposals/:id/edit.
Content: the three panels (sections left, canvas center, properties right), the top bar (Back, Title, Undo/Redo, Preview, Save, Create gold, ⋮).
Actions:
  Click a block -> the properties panel shows its fields. Edit the text, colour, data.
  Drag a block -> reorder.
  Click "Add section" -> a dropdown of block types; insert at the cursor.
  Click "Preview" -> a split pane (desktop) or modal (mobile) shows the client's view live. Read-only.
  Click "Save" -> PATCH /api/proposals/:id; a toast "Saved."
  Auto-save every 60 seconds; on session end, navigator.sendBeacon to /api/proposals/:id/autosave?token=...
  Click "Create" -> if validation passes, POST /api/proposals/:id/publish; the response has the public_id; the share modal opens.
  Click "⋮" -> Duplicate, Archive, Delete, Password (Growth/Scale), Allow PDF download (toggle).
Exit: the share modal (on Create), the proposals list (on Back), the dashboard (on Logo).
States: the auto-save indicator next to the title ("Saved" / "Saving..." / "Unsaved changes"). The validation errors scroll to the section. The loading state on Create is a spinner. The password modal has the password field (min 6) and the password-protected count.

## Flow D6 — The share modal
Entry: after "Create" (publish). Or from the ⋮ "Share" on a published document.
Content: "Your proposal is ready." The public link (copyable, mono). A message field (pre-filled). The share buttons (WhatsApp, Email, Instagram, Facebook, X, Threads, Copy Link). The line "Revercue does not send the message. You send it from your own account." If password-protected: the password shown (copyable) and "Send the password separately." "Done" (gold).
Actions:
  Click a share button -> the device's native share sheet with the link + message.
  Click "Copy Link" -> the link is copied; a toast "Link copied."
  Click "Done" -> POST /api/proposals/:id/share (log the share); the modal closes; return to the proposals list.
Exit: the proposals list.
States: the copy button shows "Copied" for 2 seconds. The share buttons are disabled if the public_id is missing (unlikely after Create).

## Flow D7 — The contract builder
Same as the proposal builder, with:
  The requirement form has contract-specific fields (which proposal is this for, scope, payment terms, revision policy, cancellation policy, after-approval dropdown).
  The canvas has no FAQs, no embedded questions. "I Have Questions" at the document level.
  The after-approval dropdown (form / invoice / pdf_only) is in the properties panel.
  The share modal pre-fills "Here is the contract for [project]. Review it and let me know if you have any questions."
  On the client side, the contract has Approve / Decline / I Have Questions.

## Flow D8 — The form editor
Same as the builder, but:
  The left panel is the question list (drag to reorder, "+ Add question", "+ Upload Markdown").
  The center panel is the question editor (text, type, options, required, explanation, adaptive branching on Growth/Scale, file upload limits).
  The right panel is the form settings (title, description, expiry date, thank-you page on Scale).
  The top bar: Back, Title, Preview, Test (runs the branching in test mode, no save), Create (gold), ⋮.
  The share modal pre-fills "I need a few details before we start. It takes about 5 minutes. [link]".
  On submit (client side), the Prompt Creator runs and the thank-you page shows (default on Free/Starter/Growth, custom on Scale).

## Flow D9 — The invoice builder
Same as the builder, but:
  The requirement form has invoice-specific fields (which contract is this for, line items, currency, tax, payment arrangement Option A/B, due date, notes).
  The center panel is the line-items table + a notes block + a payment-instructions block.
  The right panel has the payment arrangement (editable), the due date, the brand colours.
  The share modal pre-fills "Here is the invoice for [project]. You can pay via the link inside. [link]".
  On the client side, the invoice has the Buy Now button (Option A redirect / Option B account details + proof upload).
  The "Confirm payment" action is on the invoice detail (the freelancer side), which marks the invoice confirmed and adds a payment row.

## Flow D10 — The CRM list
Entry: /crm.
Content: the table (name, email, channel, last message, documents count, latest status, interest on Scale), the search, the filter (All/Active/Archived/Not interested), the sort, "+ Add client" (gold), "Export CSV".
Actions:
  Click a row -> the client detail (/crm/:clientId).
  Click "+ Add client" -> the add-client modal (name, email, company, phone, channel); POST /api/crm/clients; a toast; the list refreshes.
  Click "Export CSV" -> GET /api/crm/clients/export; the browser downloads the CSV.
  Click the ⋮ -> Edit, Archive, Mark not interested (Scale), Delete.
Exit: the client detail.
States: the table shows a skeleton. The empty state "No clients yet. Create a proposal, contract, invoice, or form — the client is added automatically. Or add one manually." + the CTA. On Free, creating a document for a new client shows a notification "Add [email] to your CRM?" (the auto-add is Starter+).

## Flow D11 — The client detail
Entry: /crm/:clientId.
Content: the header (name, email, channel, interest badge on Scale, the "Create proposal/contract/invoice/form" buttons), the communication log (the main body, a timeline), the documents (grouped by type), the notes (plan-limited), the follow-ups (with "Mark done").
Actions:
  Click "Create proposal" -> /proposals/new?client_id=:id (pre-filled).
  Click a document -> the builder or the public view.
  Click "Add note" -> a textarea; POST /api/crm/clients/:id/notes; the list refreshes.
  Click "Add communication" -> the writing area (entry type, direction, channel, message, estimated time, linked document, next step, follow-up date); POST /api/crm/clients/:id/communication; the timeline refreshes.
  Click "Mark done" on a follow-up -> PATCH /api/crm/communication/:id with follow_up_done = 1.
  Click the interest badge (Scale) -> the interest breakdown (the signals).
Exit: the builder, the public view, the CRM list.
States: the timeline shows a skeleton. The empty state "No communication yet. Add the first entry." The notes limit reached shows "You have 3 of 3 notes. Upgrade to add more." The interest breakdown is a modal.

## Flow D12 — The settings pages
Entry: /settings. The left nav (Profile, Plan & Billing, Security, Notifications, Saved FAQs, Saved Packages, Revision Prices, What Revercue Knows, Delete Account).
Content: each section is a card. The "Save changes" (gold) is disabled until a change is made. The "Cancel" (ghost) reverts.
Actions:
  Profile: name, business, website, Fiverr, services, brand colours, logo upload. PATCH /api/settings/profile.
  Plan & Billing: the current plan, the usage bars, the payment history, the upgrade/downgrade, the add-ons (Scale), the receipt download. POST /api/settings/plan/upgrade-request, /downgrade, GET /receipt/:id.
  Security: change password, 2FA toggle, active sessions list. POST /api/settings/security/change-password, /2fa, GET /sessions, POST /sessions/:id/logout, /logout-all.
  Notifications: the email notifications toggle (Growth/Scale), the per-event toggles, the newsletter toggle, the FormSubmit status card. PATCH /api/settings/notifications, POST /api/settings/formsubmit-activate.
  Saved FAQs: the list, the "Add FAQ" form, the "Keep it" button on the 10-day warning. GET/POST/DELETE /api/settings/saved-faqs, POST /:id/keep.
  Saved Packages: the list, the "Add package" form, the "Keep it" button. GET/POST/DELETE /api/settings/saved-packages, POST /:id/keep.
  Revision Prices: the category + price list. GET/PATCH /api/settings/revision-prices.
  What Revercue Knows: the read-only transparency page (Scale/Teams). GET /api/settings/what-revercue-knows.
  Delete Account: the danger card, the type-your-email confirmation, the 5-day grace, the cancel. POST /api/settings/delete-account, /cancel-deletion.
Exit: the dashboard, or the section itself.
States: the plan page shows the usage bars (red at 90%). The upgrade modal has the "Copy Payoneer email" button. The downgrade flow has the document selection. The delete account has the two-step confirmation.

# ============================================================
# PART 5 — THE CLIENT-FACING FLOW (the client's side)
# ============================================================

## Flow C1 — The client opens a proposal link
Entry: the client clicks /p/:publicId (from WhatsApp, email, wherever the freelancer sent it).
Content: the freelancer's logo and name, the proposal title, "Prepared for [Client]", the reference number, the reading time, the sections, the FAQs (collapsible), the embedded questions, the info icons, the packages (selectable), the "Next step" section, the footer (contact, "This is an offer, not a contract", the PDF download if enabled).
Actions:
  Expand an FAQ -> a tracking event (Growth+).
  Answer an embedded question -> a tracking event.
  Click "Ask a question" (if the toggle is on) -> a text box; POST /api/public/p/:publicId/question; a notification to the freelancer.
  Select a package -> a tracking event; the selection is stored.
  Click "Download PDF" (if enabled) -> the PDF.
  No Accept button. The client replies on WhatsApp or email.
Exit: none (the client leaves the page). The freelancer sees the activity.
States: the password wall if protected (enter the password, 30-min session, 3 attempts, 15-min lock). The closed page if archived ("This proposal is no longer available."). The expired banner if past the expiry date. The invalid link "This document doesn't exist or has been removed."

## Flow C2 — The client opens a contract link
Same as the proposal, plus:
  The three actions at the bottom: "Approve" (gold), "Decline" (ghost, danger border), "I Have Questions" (ghost).
  Approve: a modal "By approving, you confirm you have reviewed this contract. This is not a legally binding e-signature." Confirm -> POST /api/public/c/:publicId/action with action=approve. The contract is marked approved. If the freelancer set an after-approval action (form/invoice on Growth/Scale), the client sees the next step. Otherwise, "Approved. Thank you." + a PDF download.
  Decline: a modal "Are you sure?" + an optional reason. Confirm -> POST with action=decline. "Declined. Thank you for letting us know."
  I Have Questions: a text box; POST with action=question; the question appears on the freelancer's dashboard; the client can still approve or decline.
States: the password wall, the closed page, the expired banner, the invalid link — same as the proposal.

## Flow C3 — The client opens an invoice link
Same as the proposal, plus:
  The line items table, the subtotal/tax/total, the due date, the payment terms, the notes.
  Option A: "Buy Now" (gold) -> redirects to the freelancer's payment link.
  Option B: the account details displayed clearly + "Buy Now" -> the account details + an optional "Upload payment proof" field.
  After payment (Option B): the client uploads the proof -> POST /api/public/i/:publicId/proof. The status becomes "Proof submitted." The freelancer confirms. The client sees "Payment confirmed. Thank you." + a "Download receipt" button.
States: the overdue banner if past the due date. The password wall. The closed page.

## Flow C4 — The client opens a form link
Same as the proposal, plus:
  The questions in order, one page at a time (or all on one page, the freelancer chooses).
  The progress indicator (if multi-page).
  "Next", "Back", "Submit" (gold, disabled until the required questions are answered).
  On submit, POST /api/public/f/:publicId/submit. The response has the thank_you_config (null on Free/Starter/Growth -> the default page; the custom page on Scale).
  The default page: "Thank you. Your answers have been sent to [freelancer]." + "Powered by Revercue."
  The custom page (Scale): the freelancer's heading, body, optional button, logo.
States: the closed page if the form is closed/expired. The password wall. The client cannot submit twice (a browser cookie/session blocks the second submit with "You've already submitted this form.").

## Flow C5 — The password wall
Entry: any protected document (/p/, /c/, /i/, /f/).
Content: the centered card "This document is protected." The password field, "Continue" (gold), the error line.
Actions: enter the password -> POST /api/public/<type>/:publicId/unlock. Correct: a 30-minute signed cookie; the document opens. Wrong: "Incorrect password. 2 attempts remaining." 3 wrong: "Too many attempts. Try again in 15 minutes." The input is disabled.
Exit: the document (on success), the wall (on wrong).
States: the attempts decrement. The lock timer. The session cookie.

# ============================================================
# PART 6 — THE NOTIFICATION FLOW
# ============================================================

## Flow N1 — The bell (in-app)
Entry: any app page. The bell is in the top bar.
Content: the unread badge (the count from the page response, piggybacked). Click the bell: the dropdown with the last 10 notifications, the "Mark all as read" ghost, the "View all" ghost.
Actions:
  Click a notification -> mark as read (PATCH /api/notifications/:id/read); open the client/document.
  Click "Mark all as read" -> PATCH /api/notifications/read-all; the badge clears.
  Click "View all" -> /notifications (the full page with filters).
  Click the × on a notification -> dismiss (DELETE /api/notifications/:id).
Exit: the client/document, the notifications page.
States: the dropdown shows a skeleton while loading. The empty state "No notifications yet. You'll see client activity here."

## Flow N2 — The email (Growth/Scale/Teams)
Entry: the client opens a proposal, approves a contract, submits a form, pays an invoice.
Content: the email via FormSubmit to the freelancer's email, per the event toggle. The in-app notification is always written; the email is the opt-in layer.
Actions: the freelancer clicks the link in the email -> the client/document.
Exit: the app.
States: if the plan does not have email notifications (Free/Starter), no email. If the event toggle is off, no email. The in-app notification still appears.

# ============================================================
# PART 7 — THE ERROR AND UTILITY FLOW
# ============================================================

## Flow E1 — 404
Entry: any invalid route.
Content: "404" gold eyebrow, "This page doesn't exist." headline, "The link may be broken, or the page may have been moved." subtext, "Go to dashboard" (gold, if logged in) or "Go to home" (gold, if not), "Need help? Contact us."
Exit: the dashboard or the home.

## Flow E2 — 403
Entry: a protected route without a valid JWT, or a plan-gated route on the wrong plan.
Content: "403" gold eyebrow, "You don't have access to this." headline, "You may need to log in, or this feature may not be available on your plan." subtext, "Log in" (gold, if not logged in) or "Upgrade plan" (gold, if plan-gated) or "Go to dashboard" (ghost).
Exit: the login, the settings plan, the dashboard.

## Flow E3 — 500
Entry: any route when the Worker throws.
Content: "500" gold eyebrow, "Something went wrong." headline, "We've been notified. Try again in a moment." subtext, "Try again" (gold), "Go to dashboard" (ghost), the reference code (mono).
Exit: the retry reloads the page; the dashboard.

## Flow E4 — Offline
Entry: the browser is offline, or a fetch fails with a network error.
Content: "OFFLINE" gold eyebrow, "You're offline." headline, "Check your connection and try again. Your work is saved." subtext, "Retry" (gold), "If you were in the middle of editing, your draft is saved locally."
Exit: the retry (when back online).

## Flow E5 — Session expired
Entry: a 401 from an API call.
Content: "SESSION EXPIRED" gold eyebrow, "You've been logged out." headline, "Your session expired for security. Log in again to continue." subtext, "Log in" (gold).
Exit: /login?returnTo=<the path>. The token is cleared.

# PART 8 — THE GLOBAL RULES

Every button goes somewhere. No dead buttons.
Every form has a success state and an error state. The success state replaces the form or shows a toast. The error state is inline below the field or below the button.
Every list has an empty state (with a CTA), a loading state (skeleton), and an error state (with a retry).
Every plan gate shows the upgrade message, not a silent failure.
Every destructive action has a confirmation modal.
The 401 redirects to /session-expired (or /login if not logged in).
The 403 shows the ForbiddenPage (with the upgrade CTA if plan-gated).
The gold rule: one gold button per screen.
The auto-save: 60-second interval + session-end beacon + explicit save. The indicator is next to the title.
The FormSubmit copy is exact on every screen that mentions it.
